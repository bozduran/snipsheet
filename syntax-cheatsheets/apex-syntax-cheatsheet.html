Program structure

public class AccountService {
    public static void rename(Id accountId, String name) {
        Account a = [SELECT Id, Name FROM Account WHERE Id = :accountId];
        a.Name = name;
        update a;
    }
}
sf project deploy start --source-dir force-app
sf apex run --file scripts/apex/hello.apex
sf apex tail log
  • Apex lives in .cls and .trigger files and runs on the Salesforce platform; there is no main.
  • Code is compiled and deployed to an org. A transaction is one Apex invocation; governor limits apply per transaction.
  • Statements end in ;, blocks use { }, and every method declares a return type.
  • Use the Salesforce CLI (sf) to deploy, run anonymous Apex and stream debug logs.

Variables & operators

final Integer MAX = 10;
Integer total = 0;
total += 2;

Boolean ok = total > 0 && total < MAX;
String label = ok ? 'yes' : 'no';

if (name == null || name.trim().length() == 0) {
    name = 'Unknown';
}

Account a = null;
String owner = a?.Owner?.Name;   // safe navigation
  • Variables are explicitly typed. final means assigned once.
  • Operators follow familiar precedence: arithmetic, comparison, &&, ||, then ?:.
  • && and || short-circuit. The ternary operator is an expression.
  • Guard nullable relationships with ?. or an explicit null check.

  • Strings use single quotes. Escape a quote with a backslash.
  • Strings are immutable; methods return new strings.

  • For comparisons, be explicit: use equals or equalsIgnoreCase rather than relying on Java intuition.

Control flow

if (ready) {
    run();
} else if (fallback) {
    recover();
} else {
    throw new IllegalStateException('not ready');
}

for (Integer i = 0; i < 3; i++) { }
for (Account a : accounts) { }

while (hasMore) { }
do { work(); } while (hasMore);

switch on status {
    when 'NEW' { handleNew(); }
    when 'CLOSED', 'CANCELLED' { handleClosed(); }
    when else { handleOther(); }
}
  • switch on is the modern branching form; when else covers the default.
  • There is no fallthrough between when branches.
  • Use the enhanced for loop for lists, sets and query results.
  • Prefer returning early to deeply nested conditionals.

Classes & access

public virtual class AccountService {
    private final Id accountId;
    public String label { get; set; }

    public AccountService(Id accountId) {
        this.accountId = accountId;
    }

    public virtual void run() {
        update new Account(Id = accountId, Name = label);
    }

    public static Integer count() {
        return [SELECT COUNT() FROM Account];
    }
}
ModifierVisible to
privateonly the containing class
protectedthe class and its subclasses
publicany code in the org / namespace
globalany code, including outside a managed package
  • Methods are final by default. Mark the class virtual or abstract and the method virtual or abstract to allow overriding.
  • Properties use get; / set; accessors; a private setter is a common read-only pattern.
  • Static members belong to the class. Constructors have no return type and run on new.

Inheritance & interfaces

public interface Worker {
    void run();
}

public abstract class BaseWorker implements Worker {
    public abstract void run();
}

public class AccountWorker extends BaseWorker {
    public override void run() {
        System.debug('running');
    }
}
  • A class extends one class and implements many interfaces.
  • override is required when replacing a virtual or abstract method.
  • Abstract classes cannot be instantiated; interfaces declare behavior without state.
  • Use instanceof and casts for type checks; prefer polymorphism when the type is known.

sObjects & DML

Account a = new Account(
    Name = 'Acme',
    Industry = 'Technology'
);
insert a;

a.Name = 'Acme Inc';
update a;
upsert a External_Id__c;
delete a;

List<Account> accounts = new List<Account>{ a };
Database.SaveResult[] results = Database.insert(accounts, false);
for (Database.SaveResult r : results) {
    if (!r.isSuccess()) {
        System.debug(r.getErrors()[0].getMessage());
    }
}
  • DML statements are insert, update, upsert, delete, undelete and merge.
  • Database.insert(records, false) allows partial success and returns a result per record; inspect every result.
  • Use IDs and relationships instead of hard-coded record IDs. Savepoints can roll back part of a transaction.

SOQL & SOSL

List<Account> accounts = [
    SELECT Id, Name, (SELECT Id, LastName FROM Contacts)
    FROM Account
    WHERE Industry = :industry
    WITH SECURITY_ENFORCED
    ORDER BY Name
    LIMIT 100
];

List<List<SObject>> found = [
    FIND 'Acme' IN ALL FIELDS
    RETURNING Account(Id, Name), Contact(Id, Name)
];
  • Static SOQL uses bind variables (:industry) and is safer than string building.
  • WITH SECURITY_ENFORCED applies object and field permissions to the query.
  • Query once for a batch, then work from maps and sets. Never put SOQL inside a loop.
  • SOSL searches text across objects; SOQL queries structured records and relationships.

Triggers

trigger AccountTrigger on Account (
    before insert, before update, after update
) {
    if (Trigger.isBefore) {
        for (Account a : Trigger.new) {
            if (a.Name == null) a.Name = 'Unnamed';
        }
    }
    if (Trigger.isAfter && Trigger.isUpdate) {
        Set<Id> ids = Trigger.newMap.keySet();
        // queue related work in bulk
    }
}
  • Trigger.new, Trigger.old, Trigger.newMap and Trigger.oldMap expose the records for the current event.
  • Context flags include isBefore, isAfter, isInsert, isUpdate and isDelete.
  • Triggers fire once per bulk operation (up to 200 records), so write set-based code.
  • Guard against recursion with a static Boolean and avoid SOQL/DML inside loops.

Exceptions

try {
    insert accounts;
} catch (DmlException e) {
    System.debug(e.getMessage());
    throw new AccountException(e.getMessage());
} finally {
    cleanup();
}

public class AccountException extends Exception {
}

// Expected partial failures: use the Database methods and inspect results.
Database.SaveResult[] results = Database.insert(accounts, false);
  • Catch the most specific exception, log enough context, and rethrow or handle deliberately.
  • Custom exceptions extend Exception; constructors may call super(message).
  • finally runs whether the block succeeds or throws. Do not swallow an error just to keep going.
  • For expected per-record failures, prefer Database.insert(records, false) over one big try/catch.

Async Apex

@future(callout=true)
public static void syncAccount(Id accountId) {
    // one-off callout or slow work
}

public class Job implements Queueable {
    public void execute(QueueableContext ctx) { }
}
System.enqueueJob(new Job());

public class Cleanup implements Database.Batchable<SObject> {
    public Database.QueryLocator start(Database.BatchableContext bc) {
        return Database.getQueryLocator('SELECT Id FROM Account');
    }
    public void execute(Database.BatchableContext bc, List<Account> scope) { }
    public void finish(Database.BatchableContext bc) { }
}
ToolUse it when
@futurea simple one-off job; callouts with callout=true
Queueablestructured jobs, chaining and state
Batchablelarge data sets that exceed synchronous limits
Schedulablecron-style recurring execution
  • Async work runs in a separate transaction with separate limits.
  • @future methods are static, return void, and accept only supported primitive/collection parameters; pass IDs, not sObjects.
  • Queueable can chain jobs; Batchable processes chunks and has start/execute/finish phases.
  • Make async jobs idempotent and observable; failures are easy to miss.

Testing

@IsTest
private class AccountServiceTest {
    @TestSetup
    static void makeData() {
        insert new Account(Name = 'Acme');
    }

    @IsTest
    static void renamesAccount() {
        Account a = [SELECT Id FROM Account LIMIT 1];
        Test.startTest();
        AccountService.rename(a.Id, 'Acme 2');
        Test.stopTest();
        System.assertEquals(
            'Acme 2',
            [SELECT Name FROM Account WHERE Id = :a.Id].Name
        );
    }
}
  • @IsTest classes do not count toward org limits and see only their own test data by default.
  • @TestSetup creates shared data once per test class; each test still gets a fresh transaction.
  • Test.startTest() and stopTest() isolate the code under test and reset governor limits.
  • Mock callouts with Test.setMock; never make real callouts from tests. Org coverage must still be at least 75%.

Security & sharing

public with sharing class AccountController {
    @AuraEnabled
    public static List<Account> recent() {
        return [
            SELECT Id, Name
            FROM Account
            WITH SECURITY_ENFORCED
            ORDER BY LastModifiedDate DESC
            LIMIT 20
        ];
    }
}

SObjectAccessDecision d =
    Security.stripInaccessible(AccessType.READABLE, records);
List<Account> readable = (List<Account>) d.getRecords();
  • with sharing enforces record-level sharing; without sharing ignores it; inherited sharing uses the caller.
  • Enforce CRUD/FLS with WITH SECURITY_ENFORCED or Security.stripInaccessible.
  • Bind variables in SOQL. For dynamic filters, escape with String.escapeSingleQuotes.
  • Store secrets in Named Credentials, not custom settings or source code.

Callouts & JSON

HttpRequest req = new HttpRequest();
req.setEndpoint('callout:My_Named_Credential/users');
req.setMethod('GET');
req.setHeader('Accept', 'application/json');
req.setTimeout(10000);

HttpResponse res = new Http().send(req);
if (res.getStatusCode() == 200) {
    Map<String, Object> body =
        (Map<String, Object>) JSON.deserializeUntyped(res.getBody());
}

String json = JSON.serialize(new Map<String, Object>{'id' => 1});
Account parsed = (Account) JSON.deserialize(json, Account.class);
  • Named Credentials keep endpoints and secrets out of code. Callouts count against limits and need timeouts.
  • After uncommitted DML, a callout in the same transaction fails; move it to async or do the callout first.
  • deserializeUntyped returns generic maps/lists; deserialize maps into a typed class.
  • Use Test.setMock(HttpCalloutMock.class, ...) in tests.

Common gotchas

  • SOQL or DML inside a loop is the classic governor-limit failure. Bulkify.
  • Null relationships throw; use safe navigation or check before dereferencing.
  • Hard-coded record IDs fail across orgs and sandboxes. Query or configure IDs.
  • Triggers are bulk operations. A static recursion guard is not a substitute for idempotent logic.
  • @future methods cannot receive sObjects; pass IDs and re-query.
  • Callouts after uncommitted DML fail; call out first or use async.
  • Test data is invisible to other tests unless created in @TestSetup or the test itself.
  • Ignoring Database.SaveResult hides partial DML failures.
